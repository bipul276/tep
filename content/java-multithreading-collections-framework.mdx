# Java Multithreading, Concurrency, and Collections Framework

Object-Oriented Programming examinations in **UGC NET** and **Bihar STET** consistently emphasize core Java multi-threaded execution, memory visibility, lock monitors, and the internal data structures of the Java Collections Framework (JCF).

---

## 1. Java Thread Lifecycle and Execution

In Java, threads are managed by the JVM and map directly to native operating system threads.

### 1.1 Thread States (`Thread.State` Enum)
1. **NEW**: A thread that has been instantiated (`new MyThread()`) but not yet started via `.start()`.
2. **RUNNABLE**: A thread executing in the JVM or waiting for CPU allocation from the operating system scheduler.
3. **BLOCKED**: A thread waiting to acquire an intrinsic monitor lock to enter or re-enter a `synchronized` block/method.
4. **WAITING**: A thread waiting indefinitely for another thread to perform a particular action (called `Object.wait()`, `Thread.join()`, or `LockSupport.park()`).
5. **TIMED_WAITING**: A thread waiting for a specified timeout period (called `Thread.sleep(millis)`, `Object.wait(timeout)`, or `Thread.join(timeout)`).
6. **TERMINATED**: A thread that has completed execution of its `run()` method.

<Callout type="warning">
**Crucial Exam Distinctions**:
- Calling `thread.run()` executes the code synchronously on the **current calling thread** like a regular method!
- Calling `thread.start()` allocates a **new call stack** and triggers asynchronous execution in a new thread.
</Callout>

### 1.2 Thread Synchronization & Inter-Thread Communication
Every Java object has an intrinsic lock (monitor).
- **`synchronized` Method / Block**: Ensures mutual exclusion. Only one thread can hold the object monitor lock at a time.
- **`wait()`, `notify()`, `notifyAll()`**: Defined in the **`java.lang.Object`** class (NOT `Thread`!), because locks belong to objects, not threads. Must be invoked strictly from inside a `synchronized` context; otherwise, `IllegalMonitorStateException` is thrown at runtime!
- **`Thread.sleep()` vs `Object.wait()`**:
  - `sleep()` keeps the monitor lock held while pausing.
  - `wait()` **releases the monitor lock** so other threads can proceed!

## 2. Java Collections Framework (JCF)

The JCF provides a unified architecture for storing and manipulating groups of objects.

### 2.1 Collection Hierarchy
```
             Iterable<E>
                 │
            Collection<E>
        ┌────────┼────────┐
      List<E>  Set<E>   Queue<E>
        │        │
  ArrayList   HashSet
  LinkedList  TreeSet (SortedSet)
```
*(Note: `Map<K, V>` does NOT inherit from `Collection<E>` or `Iterable`!)*

### 2.2 List vs. Set vs. Map Comparisons

| Data Structure | Underlying Storage | Duplicates Allowed? | Order Maintained? | Lookup Time | Thread Safe? |
| :--- | :--- | :---: | :---: | :---: | :---: |
| **`ArrayList`** | Resizable Dynamic Array | Yes | Insertion Order | $O(1)$ random access by index | No |
| **`LinkedList`** | Doubly-Linked List | Yes | Insertion Order | $O(n)$ search, $O(1)$ add at ends | No |
| **`HashSet`** | Backed by `HashMap` | **No** | Unordered | $O(1)$ average | No |
| **`TreeSet`** | Red-Black Tree | **No** | Natural / Sorted Order | $O(\log n)$ | No |
| **`HashMap`** | Hash Table (Buckets) | Keys: No, Values: Yes | Unordered | $O(1)$ average | No |
| **`TreeMap`** | Red-Black Tree | Keys: No, Values: Yes | Sorted by Key | $O(\log n)$ | No |
| **`Hashtable`** | Hash Table | No null keys/values | Unordered | $O(1)$ | **Yes (Synchronized)** |

### 2.3 Internal Working of `HashMap`
In Java 8+, `HashMap` resolves collisions using separate chaining:
1. Computes `hash(key) = (h = key.hashCode()) ^ (h >>> 16)`.
2. Bucket index = `(n - 1) & hash`.
3. If collision occurs, nodes form a linked list.
4. **Treeification**: If a single bucket list exceeds **8 nodes** (`TREEIFY_THRESHOLD = 8`) and total table capacity is at least 64, the linked list is converted into a balanced **Red-Black Tree**, reducing worst-case lookup from $O(n)$ down to **$O(\log n)$**!

## 3. Exception Handling Architecture

- **`Throwable`**: Root of the Java exception hierarchy.
  - **`Error`**: Serious hardware or JVM problems that applications should not catch (`OutOfMemoryError`, `StackOverflowError`).
  - **`Exception`**:
    - **Checked Exceptions**: Subclasses of `Exception` excluding `RuntimeException`. Verified at compile-time; MUST be declared via `throws` or caught via `try-catch` (`IOException`, `SQLException`).
    - **Unchecked Exceptions**: Subclasses of `RuntimeException`. Not enforced by compiler (`NullPointerException`, `ArrayIndexOutOfBoundsException`, `ArithmeticException`).
