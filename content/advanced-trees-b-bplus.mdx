# Advanced Tree Structures: B-Trees, B+ Trees, Node Splitting, and DBMS Indexing

In large-scale database management systems (DBMS) and file systems, data datasets span gigabytes and terabytes, far exceeding available main memory (RAM). When data resides on secondary storage (magnetic disks or SSDs), disk block I/O is the dominant performance bottleneck.

In the **UGC NET Computer Science** syllabus (both Unit 3 Data Structures and Unit 4 DBMS segments), **B-Trees and B+ Trees** constitute a primary source of high-yield numerical calculations:
1. **The I/O Model & Multi-Way Tree Rationale** (Why AVL and Red-Black trees fail on secondary storage).
2. **B-Tree Structural Properties & Invariants** (Order $m$, minimum/maximum keys, height bounds).
3. **B+ Tree Architecture** (Structural separation of index and data, range query superiority).
4. **Node Splitting and Merging Mechanics** (Insertion overflow, deletion underflow, borrowing).
5. **DBMS Index Block Calculations** (Formulas for maximum order, leaf capacity, and I/O access bounds).

---

## 1. The Secondary Storage Bottleneck & The Multi-Way Rationale

Traditional balanced binary search trees (AVL Trees, Red-Black Trees) guarantee worst-case search complexity of:

$$T_{\text{search}} = O(\log_2 N)$$

While optimal in RAM (where access times are $\approx 10 - 50\,\text{ns}$), binary trees perform terribly on disk storage:
- Reading a random block from magnetic disk involves mechanical arm seek time and rotational latency ($\approx 5 - 10\,\text{ms} = 5 \times 10^6\,\text{ns}$, roughly $100,000\times$ slower than RAM).
- For a database with $N = 10^7$ records, a binary tree has height $\log_2(10^7) \approx 24$. Searching a record requires up to **24 random disk block I/Os**, taking $24 \times 10\,\text{ms} = 240\,\text{ms}$ per query.

### The Multi-Way Solution
Instead of a branching factor of 2, a **Multi-Way Search Tree of Order $m$** sizes each tree node to match the operating system's physical **Disk Block Size** (typically $4\,\text{KB}$ or $8\,\text{KB}$):
- With fan-out $m = 512$, tree height drops to:
$$h = \lceil \log_{512}(10^7) \rceil \approx 3$$
- A search requires at most **3 disk block accesses** ($\approx 30\,\text{ms}$), achieving a dramatic $8\times$ performance improvement.

## 2. B-Tree Formal Properties & Invariants

A **B-Tree of Order $m$** (introduced by Rudolf Bayer and Edward McCreight in 1970) is a self-balancing, multi-way search tree that satisfies the following non-negotiable structural properties:

```
                          [ 20  |  50 ]
                         /      |      \
                        ▼       ▼       ▼
                  [ 5 | 10 ] [ 30 | 40 ] [ 60 | 70 | 80 ]
```

### 2.1 The Cardinal Invariants

1. **Root Node Invariant**:
   - The root has at least **1 key** (if $N \ge 1$) and at least **2 child pointers** (unless the tree has only 1 node).
   - The root has at most **$m - 1$ keys** and at most **$m$ children**.
2. **Internal Node Invariant**:
   - Every internal node (non-root, non-leaf) has at least $\lceil m/2 \rceil$ children and at least $\lceil m/2 \rceil - 1$ keys.
   - Every internal node has at most $m$ children and at most $m - 1$ keys.
3. **Leaf Node Invariant**:
   - All leaf nodes appear at the **exact same depth** (perfectly balanced tree).
   - Every leaf node holds between $\lceil m/2 \rceil - 1$ and $m - 1$ keys.
4. **Key-to-Child Relationship**:
   - An internal node containing $k$ keys contains exactly **$k + 1$ child pointers**.
5. **Ordering Property**:
   - Keys within a node are stored in strictly ascending order: $K_1 < K_2 < \dots < K_k$.
   - For any key $K_i$ in an internal node, all keys in subtree $P_{i-1}$ are $< K_i$, and all keys in subtree $P_i$ are $> K_i$.

```
+--------------------+-----------------------------+-----------------------------+
| Entity             | Minimum Allowed             | Maximum Allowed             |
+--------------------+-----------------------------+-----------------------------+
| Children (Root)    | **2**                       | **m**                       |
| Keys (Root)        | **1**                       | **m - 1**                   |
| Children (Internal)| **m / 2**                 | **m**                       |
| Keys (Internal)    | **m / 2 - 1**             | **m - 1**                   |
| Keys (Leaf)        | **m / 2 - 1**             | **m - 1**                   |
+--------------------+-----------------------------+-----------------------------+
```

---

### 2.2 Maximum and Minimum Height Bounds

For a B-Tree of order $m$ storing $N$ total keys:

#### 1. Maximum Possible Number of Keys at Height $h$ (Root at $h = 0$):
$$N_{\max} = m^{h+1} - 1$$

#### 2. Minimum Height (Best Case - Every node completely full):
$$h_{\min} = \lceil \log_m (N + 1) \rceil - 1$$

#### 3. Maximum Height (Worst Case - Every node has minimum keys $\lceil m/2 \rceil - 1$):
$$h_{\max} \le \left\lfloor \log_{\lceil m/2 \rceil} \left(\frac{N + 1}{2}\right) \right\rfloor$$

## 3. B+ Tree Architecture & Distinction from B-Tree

While B-Trees store data record pointers in both internal nodes and leaf nodes, the **B+ Tree** introduces a complete separation between indexing logic and actual data storage.

```
 B-Tree Internal Node:
   [ P0 | (Key1, RecPtr1) | P1 | (Key2, RecPtr2) | P2 ]  <-- Bulky; small fan-out m!

 B+ Tree Internal Node:
   [ P0 | Key1 | P1 | Key2 | P2 ]                         <-- Slim; massive fan-out m!
 
 B+ Tree Leaf Nodes (Doubly-Linked):
   [ (Key1, RecPtr1) | (Key2, RecPtr2) | NextPtr ] <═══► [ (Key3, RecPtr3) | ... ]
```

### 3.1 Detailed Architectural Comparison

```
+--------------------------+------------------------------------------+------------------------------------------+
| Architectural Property   | Standard B-Tree                          | B+ Tree                                  |
+--------------------------+------------------------------------------+------------------------------------------+
| Key Placement            | Search keys stored in internal nodes     | Search keys replicated; **ALL** keys and |
|                          | and leaf nodes (no duplicates)           | data pointers reside in leaf nodes       |
+--------------------------+------------------------------------------+------------------------------------------+
| Data Record Pointers     | Attached to keys at every level          | Confined strictly to the leaf level      |
+--------------------------+------------------------------------------+------------------------------------------+
| Internal Node Size       | Large (stores keys + record pointers)    | Small (stores only search keys + child P)|
+--------------------------+------------------------------------------+------------------------------------------+
| Index Fan-Out ($m$)      | **Lower** (fewer pointers fit in a block)| **Significantly Higher** ($2\times-3\times$ larger)|
+--------------------------+------------------------------------------+------------------------------------------+
| Tree Height for same $N$ | Taller ($h_{\text{B}} > h_{\text{B+}}$)  | **Shorter** (fewer disk I/O operations)  |
+--------------------------+------------------------------------------+------------------------------------------+
| Sequential / Range Scans | **Inefficient** (requires expensive      | **Extremely Fast $O(k)$** (traverses     |
| (e.g., `WHERE age > 25`) | in-order depth-first tree traversal)     | sequential linked-list at leaf level)    |
+--------------------------+------------------------------------------+------------------------------------------+
| Search Time Variability  | Variable ($O(1)$ at root, $O(h)$ at leaf)| **Uniform** (every search reaches leaf)  |
+--------------------------+------------------------------------------+------------------------------------------+
```

## 4. Node Splitting and Merging Mechanics

### 4.1 B-Tree Insertion & Splitting

1. Search the tree to locate the correct leaf node for key insertion.
2. If the leaf has $< m - 1$ keys, insert the key in sorted order.
3. If the leaf has $m - 1$ keys, inserting the new key causes an **Overflow** ($m$ keys):
   - Identify the **Median Key** at position $\lceil m/2 \rceil$.
   - **Split** the node into two sibling nodes:
     - Left node receives keys before the median: indices $1$ to $\lceil m/2 \rceil - 1$.
     - Right node receives keys after the median: indices $\lceil m/2 \rceil + 1$ to $m$.
   - **Promote** the median key up into the parent node (removing it from the leaf).
   - If the parent also overflows, propagate the split upward recursively.
   - If the root splits, create a new root containing the promoted median key and two child pointers (**tree height increases by 1**).

---

### 4.2 B+ Tree Insertion & Splitting (Replication vs. Promotion)

> **Critical Distinction**: In a B+ Tree, leaf nodes must retain all keys to support point and range queries.

```
 Leaf Split in B+ Tree (Order m = 4, Max Keys = 3):
   Insert 25 into [ 10 | 20 | 30 ]  ──► Overflow [ 10 | 20 | 25 | 30 ]
   
   Result:
   Parent:                  [ 25 ]
                           /      \
   Leaves:          [ 10 | 20 ] ──► [ 25 | 30 ]  (Notice 25 is COPIED into leaf!)
```

1. **Leaf Node Split**:
   - The median key is **copied (replicated)** to the parent node.
   - The median key **remains** as the smallest key of the right leaf sibling.
   - The left sibling's `next` pointer is updated to point to the right sibling.
2. **Internal Node Split**:
   - Follows the standard B-Tree rule: the median key is **promoted (moved)** up to the parent and **removed** from the internal node.

---

### 4.3 Deletion & Merging (Underflow Handling)

When a key is deleted from a node causing its key count to fall below the minimum threshold $\lceil m/2 \rceil - 1$:

1. **Borrowing / Redistribution (Sibling has spare keys)**:
   - If an immediate adjacent sibling has $> \lceil m/2 \rceil - 1$ keys:
   - Borrow a key from the sibling via the parent (rotate key through parent).
2. **Merging (Sibling has exactly minimum keys)**:
   - If no adjacent sibling has keys to spare:
   - **Merge** the underflowing node with its sibling and pull down the separating key from the parent.
   - If the parent underflows as a consequence, propagate merging upward.
   - If the root becomes empty (0 keys, 1 child), the root is discarded and its single child becomes the new root (**tree height decreases by 1**).

## 5. DBMS Indexing & Disk Block Calculations

The design of a B/B+ tree index begins with calculating the maximum order $m$ that fits within an operating system disk block.

### Parameter Definitions:
- $B$: Disk Block Size (bytes).
- $K$: Search Key Size (bytes).
- $P$: Block Pointer Size (bytes).
- $R_p$: Record Pointer Size (bytes).
- $P_{\text{next}}$: Leaf Sibling Pointer Size (bytes).

---

### 5.1 Internal Node Order Formula (B+ Tree)

An internal node of order $m$ contains $m$ block pointers and $m - 1$ search keys:

$$m \cdot P + (m - 1) \cdot K \le B$$

Solving for maximum order $m$:

$$m(P + K) - K \le B \implies m = \left\lfloor \frac{B + K}{P + K} \right\rfloor$$

---

### 5.2 Leaf Node Capacity Formula (B+ Tree)

A leaf node contains $L$ data records (each consisting of a key and a record pointer) plus one sibling pointer $P_{\text{next}}$:

$$L \cdot (K + R_p) + P_{\text{next}} \le B$$

Solving for maximum leaf capacity $L$:

$$L = \left\lfloor \frac{B - P_{\text{next}}}{K + R_p} \right\rfloor$$

## 6. Worked Numerical Examples & Computations

### Numerical 1: Order and Leaf Capacity Calculation
**Problem (UGC NET December 2019 / Official PYQ)**:
A database system uses disk blocks of size $B = 512\,\text{bytes}$. The search key size is $K = 9\,\text{bytes}$, the record pointer size is $R_p = 7\,\text{bytes}$, and the block pointer size is $P = 6\,\text{bytes}$. For a B+ Tree index:
1. Calculate the maximum order $m$ of an internal node.
2. Calculate the maximum number of record entries $L$ that can be stored in a leaf node (assume $P_{\text{next}} = 6\,\text{bytes}$).

#### Solution:
1. **Internal Node Order ($m$)**:
$$m \cdot P + (m - 1) \cdot K \le B$$
$$m(6) + (m - 1)(9) \le 512$$
$$6m + 9m - 9 \le 512$$
$$15m \le 521 \implies m = \left\lfloor \frac{521}{15} \right\rfloor = 34$$
   > **Maximum Order of Internal Node**: $m = 34$.

2. **Leaf Node Capacity ($L$)**:
$$L \cdot (K + R_p) + P_{\text{next}} \le B$$
$$L(9 + 7) + 6 \le 512$$
$$16L + 6 \le 512 \implies 16L \le 506$$
$$L = \left\lfloor \frac{506}{16} \right\rfloor = 31$$
   > **Maximum Leaf Capacity**: $L = 31$ records per leaf block.

---

### Numerical 2: Number of Block Accesses for 1 Million Records
**Problem**: A relational table contains $N = 1,000,000$ records. A B+ Tree index has internal node order $m = 100$ and leaf capacity $L = 50$. Assuming nodes are filled to an average occupancy of $67\%$ ($2/3$ full):
1. How many leaf blocks are required?
2. What is the total height of the B+ Tree?
3. How many disk block accesses are required to retrieve a single record?

#### Solution:
1. **Average Leaf Occupancy**:
$$\text{Keys per Leaf} = 0.67 \times 50 \approx 33\,\text{records/block}$$
$$\text{Total Leaf Blocks} = \left\lceil \frac{1,000,000}{33} \right\rceil = 30,304\,\text{blocks}$$

2. **Average Internal Node Fan-Out**:
$$\text{Average Fan-Out} = 0.67 \times 100 \approx 67\,\text{pointers/node}$$

3. **Level Calculations (Counting bottom-up from leaves)**:
   - Level 0 (Leaves): $30,304$ blocks
   - Level 1: $\lceil 30,304 / 67 \rceil = 453$ blocks
   - Level 2: $\lceil 453 / 67 \rceil = 7$ blocks
   - Level 3 (Root): $\lceil 7 / 67 \rceil = 1$ root block

$$\text{Tree Height} = 3 \quad (\text{Root at Level 3} \to \text{Level 2} \to \text{Level 1} \to \text{Leaf at Level 0})$$

4. **Total Disk Block Accesses**:
$$\text{Disk Accesses} = \text{Tree Height} + 1\,\text{access for actual data block} = 3 + 1 = 4\,\text{block I/Os}$$

*(Searching among 1 million records requires only 4 block transfers from disk).*

## 8. High-Yield Revision Matrix

| Concept | Key Mathematical Formula / Rule | Common Exam Trap |
|---|---|---|
| **Internal Node Order** | $m \cdot P + (m - 1) \cdot K \le B$ | Forgetting the $(m - 1)$ coefficient on the key size |
| **Leaf Node Capacity** | $L \cdot (K + R_p) + P_{\text{next}} \le B$ | Omitting the record pointer $R_p$ at the leaf level |
| **Minimum Keys (Internal)** | $\lceil m/2 \rceil - 1$ keys | Confusing minimum keys with minimum children ($\lceil m/2 \rceil$) |
| **Root Exceptions** | Min keys: $1$; Min children: $2$ | Applying the $\lceil m/2 \rceil$ rule to the root node |
| **B+ Leaf Split** | Median key is **replicated** to parent | Believing the median is removed from the leaf |
| **Tree Balance** | All leaves at strictly the same depth | Thinking B-Trees can have leaves at varying levels like AVL |
