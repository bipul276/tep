# Deadlocks and Banker's Algorithm: Handling, Avoidance, and Detection

In a multiprogramming operating system, processes compete for a finite set of non-shareable resources. When two or more processes are permanently blocked because each holds resources that the others require to proceed, the system enters a **Deadlock** state.

For competitive examinations (**UGC NET** and **Bihar STET Computer Science**), deadlock analysis centers around **Coffman's four conditions**, **Resource Allocation Graph (RAG) topology**, the **Banker's Algorithm (Safety and Resource-Request)**, and **Recovery mechanisms**.

---

## 1. Formal Definition and Coffman's Four Conditions

A set of processes is in a deadlock state when every process in the set is waiting for an event that can only be caused by another process in the same set.

For a deadlock to arise, all **four Coffman conditions** must hold simultaneously. Eliminating even **one** condition guarantees that a deadlock cannot occur:

```
+-----------------------------------------------------------------------------------------+
|                              COFFMAN'S FOUR CONDITIONS                                  |
+-------------------+---------------------------------------------------------------------+
| Condition         | Operating System Meaning & Elimination Strategy                     |
+-------------------+---------------------------------------------------------------------+
| 1. Mutual         | At least one resource must be held in a non-shareable mode.         |
|    Exclusion      | Prevention: Spooling (e.g., printer spooler). Shareable resources   |
|                   | (read-only files) never cause deadlocks.                            |
+-------------------+---------------------------------------------------------------------+
| 2. Hold and Wait  | A process must hold at least one resource while waiting to acquire  |
|                   | additional resources held by other processes.                       |
|                   | Prevention: Require processes to request all resources at once,     |
|                   | or release currently held resources before making new requests.     |
+-------------------+---------------------------------------------------------------------+
| 3. No Preemption  | Resources cannot be forcibly seized; they can only be released      |
|                   | voluntarily by the holding process upon task completion.            |
|                   | Prevention: If a process requesting a resource is denied, it must   |
|                   | release all its currently held resources (preemption).              |
+-------------------+---------------------------------------------------------------------+
| 4. Circular Wait  | A closed directed chain of processes exists:                        |
|                   | $P_0 \to P_1 \to P_2 \to \dots \to P_n \to P_0$, where each $P_i$   |
|                   | waits for a resource held by $P_{(i+1) \bmod (n+1)}$.               |
|                   | Prevention: Impose a global strict linear ordering on resources:    |
|                   | $F: R \to \mathbb{N}$; requests must be made in strictly ascending order.|
+-------------------+---------------------------------------------------------------------+
```

> [!IMPORTANT]
> **Havender's Linear Ordering**: Imposing a total ordering $F(R_i)$ and requiring that processes request resources only in strictly increasing order ($F(R_{next}) > F(R_{current})$) mathematically disallows the creation of a directed cycle, thus eliminating **Circular Wait**.

## 2. Resource Allocation Graphs (RAG)

A **Resource Allocation Graph (RAG)** is a directed graph $G = (V, E)$ used to model resource distribution:
- **Vertices $V$**: Partitioned into two disjoint sets:
  - Process Nodes: $P = \{P_1, P_2, \dots, P_n\}$ (represented by circles).
  - Resource Nodes: $R = \{R_1, R_2, \dots, R_m\}$ (represented by rectangles containing dots corresponding to available instances).
- **Edges $E$**:
  - **Request Edge**: Directed edge from Process to Resource ($P_i \to R_j$). Process $P_i$ has requested an instance of $R_j$ and is currently waiting.
  - **Assignment Edge**: Directed edge from Resource instance to Process ($R_j \to P_i$). An instance of $R_j$ has been allocated to $P_i$.

```
     Single-Instance RAG (Cycle = Deadlock)         Multi-Instance RAG (Cycle != Deadlock)
           [ R1 (•) ]                                   [ R1 (••) ]
           ↗        \                                   ↗         \
          /          ▼                                 /           ▼
       ( P1 )       ( P2 )                          ( P1 )        ( P2 )
          ▲          /                                 ▲          /
           \        ↙                                   \        ↙
           [ R2 (•) ]                                   [ R2 (••) ]
                                                       /           \
                                                      ▼             ▼
                                                    ( P3 )        ( P4 )
```

### The Fundamental RAG Theorem
1. **Single-Instance Resources (Every resource has exactly 1 instance)**:
$$\text{A cycle in the RAG} \iff \text{Deadlock exists (Necessary and Sufficient condition)}$$
2. **Multi-Instance Resources (Resources have $\ge 1$ instances)**:
$$\text{A cycle in the RAG} \implies \text{Deadlock MAY exist (Necessary, but NOT Sufficient)}$$
   - A cycle is a prerequisite for a deadlock, but if there are external processes holding instances of the cycled resources that can finish and break the cycle, no deadlock occurs.
   - A **Knot** (a directed subgraph where every reachable node can reach every other node in the subgraph) in a multi-instance graph is a **sufficient** condition for deadlock.

### Safe, Unsafe, and Deadlock States

```
+-----------------------------------------------------------+
|                       ALL STATES                          |
|  +-----------------------------------------------------+  |
|  |                    UNSAFE STATES                    |  |
|  |  +-----------------------------------------------+  |  |
|  |  |               DEADLOCK STATES                 |  |  |
|  |  +-----------------------------------------------+  |  |
|  +-----------------------------------------------------+  |
|  +-----------------------------------------------------+  |
|  |                     SAFE STATES                     |  |
|  |  (Guaranteed safe sequence exists; NO deadlock)     |  |
|  +-----------------------------------------------------+  |
+-----------------------------------------------------------+
```

- **Safe State**: A state is safe if there exists a **Safe Sequence** $\langle P_1, P_2, \dots, P_n \rangle$ such that for each $P_i$, the maximum resources that $P_i$ may still request can be satisfied by the currently available resources plus the resources already held by all $P_j$ (where $j < i$).
- **Unsafe State**: Not every unsafe state is a deadlock; however, an unsafe state **may lead** to a deadlock if processes request their maximum claims simultaneously.
- **Deadlock Avoidance Goal**: Ensure the OS never transitions from a **Safe State** to an **Unsafe State**.

## 4. The Banker's Algorithm (Dijkstra)

The Banker's Algorithm is a classic deadlock avoidance algorithm applicable to systems with multiple instances of each resource type.

### 4.1 Data Structures
Let $n$ be the number of processes and $m$ be the number of resource types:
1. $\text{Available}[m]$: Vector of length $m$. If $\text{Available}[j] = k$, there are $k$ instances of resource type $R_j$ currently available.
2. $\text{Max}[n][m]$: $n \times m$ matrix. If $\text{Max}[i][j] = k$, process $P_i$ may request at most $k$ instances of $R_j$.
3. $\text{Allocation}[n][m]$: $n \times m$ matrix. If $\text{Allocation}[i][j] = k$, process $P_i$ is currently allocated $k$ instances of $R_j$.
4. $\text{Need}[n][m]$: $n \times m$ matrix. Remaining resource need for process $P_i$:
$$\text{Need}[i][j] = \text{Max}[i][j] - \text{Allocation}[i][j]$$

---

### 4.2 The Safety Algorithm
Determines whether a system state is safe:

1. Let $\text{Work}$ be a vector of length $m$, initialized to $\text{Available}$:
$$\text{Work} = \text{Available}$$
   Let $\text{Finish}$ be a boolean vector of length $n$, initialized to $\text{false}$:
$$\text{Finish}[i] = \text{false} \quad \text{for } i = 0, 1, \dots, n-1$$

2. Find an index $i$ such that:
$$\text{Finish}[i] == \text{false} \quad \text{and} \quad \text{Need}[i] \le \text{Work}$$
   If no such $i$ exists, proceed to **Step 4**.

3. Process $P_i$ can finish. It releases all allocated resources:
$$\text{Work} = \text{Work} + \text{Allocation}[i]$$
$$\text{Finish}[i] = \text{true}$$
   Return to **Step 2**.

4. If $\text{Finish}[i] == \text{true}$ for all $i \in \{0, 1, \dots, n-1\}$, the system is in a **Safe State**. The order in which processes finished constitutes a valid **Safe Sequence**.

**Time Complexity**: $O(m \cdot n^2)$, because in the worst case, searching for a satisfiable process requires examining $n$ candidates across $n$ rounds, each comparing $m$ resource types.

---

### 4.3 The Resource-Request Algorithm
When process $P_i$ makes a request vector $\text{Request}_i$:

1. If $\text{Request}_i \le \text{Need}[i]$, proceed to Step 2. Otherwise, raise an error: **Process exceeded its declared maximum claim**.
2. If $\text{Request}_i \le \text{Available}$, proceed to Step 3. Otherwise, $P_i$ must **wait** (insufficient resources available).
3. The OS pretends to allocate the requested resources by modifying the state speculatively:
$$\text{Available} = \text{Available} - \text{Request}_i$$
$$\text{Allocation}[i] = \text{Allocation}[i] + \text{Request}_i$$
$$\text{Need}[i] = \text{Need}[i] - \text{Request}_i$$
4. Run the **Safety Algorithm**:
   - If the resulting state is **Safe**, the transaction completes, and resources are allocated to $P_i$.
   - If the resulting state is **Unsafe**, $P_i$ must wait, and the prior allocation state is **restored** (rolled back).

## 5. Comprehensive Worked Numerical Problem

Consider 5 processes $\{P_0, P_1, P_2, P_3, P_4\}$ and 3 resource types $\{A, B, C\}$ with total instances:
$$\text{Total} = (A: 10, B: 5, C: 7)$$

### Current Snapshot:

| Process | Allocation ($A, B, C$) | Max ($A, B, C$) | Available ($A, B, C$) |
|:---:|:---:|:---:|:---:|
| $P_0$ | $(0, 1, 0)$ | $(7, 5, 3)$ | $(3, 3, 2)$ |
| $P_1$ | $(2, 0, 0)$ | $(3, 2, 2)$ | |
| $P_2$ | $(3, 0, 2)$ | $(9, 0, 2)$ | |
| $P_3$ | $(2, 1, 1)$ | $(2, 2, 2)$ | |
| $P_4$ | $(0, 0, 2)$ | $(4, 3, 3)$ | |

---

### Step 1: Compute the Need Matrix ($\text{Need} = \text{Max} - \text{Allocation}$)

$$\text{Need}[P_0] = (7-0, 5-1, 3-0) = \mathbf{(7, 4, 3)}$$
$$\text{Need}[P_1] = (3-2, 2-0, 2-0) = \mathbf{(1, 2, 2)}$$
$$\text{Need}[P_2] = (9-3, 0-0, 2-2) = \mathbf{(6, 0, 0)}$$
$$\text{Need}[P_3] = (2-2, 2-1, 2-1) = \mathbf{(0, 1, 1)}$$
$$\text{Need}[P_4] = (4-0, 3-0, 3-2) = \mathbf{(4, 3, 1)}$$

---

### Step 2: Execute the Safety Algorithm

Initial State:
$$\text{Work} = (3, 3, 2)$$
$$\text{Finish} = [\text{false}, \text{false}, \text{false}, \text{false}, \text{false}]$$

1. **Test $P_0$**: $\text{Need}[P_0] = (7, 4, 3) \le (3, 3, 2) \implies \text{FALSE}$. Cannot proceed.
2. **Test $P_1$**: $\text{Need}[P_1] = (1, 2, 2) \le (3, 3, 2) \implies \mathbf{TRUE}$.
   - $P_1$ executes and finishes.
   - $\text{Work} = \text{Work} + \text{Allocation}[P_1] = (3, 3, 2) + (2, 0, 0) = \mathbf{(5, 3, 2)}$.
   - $\text{Finish}[P_1] = \text{true}$.
3. **Test $P_3$**: $\text{Need}[P_3] = (0, 1, 1) \le (5, 3, 2) \implies \mathbf{TRUE}$.
   - $P_3$ executes and finishes.
   - $\text{Work} = (5, 3, 2) + (2, 1, 1) = \mathbf{(7, 4, 3)}$.
   - $\text{Finish}[P_3] = \text{true}$.
4. **Test $P_4$**: $\text{Need}[P_4] = (4, 3, 1) \le (7, 4, 3) \implies \mathbf{TRUE}$.
   - $P_4$ executes and finishes.
   - $\text{Work} = (7, 4, 3) + (0, 0, 2) = \mathbf{(7, 4, 5)}$.
   - $\text{Finish}[P_4] = \text{true}$.
5. **Test $P_0$**: $\text{Need}[P_0] = (7, 4, 3) \le (7, 4, 5) \implies \mathbf{TRUE}$.
   - $P_0$ executes and finishes.
   - $\text{Work} = (7, 4, 5) + (0, 1, 0) = \mathbf{(7, 5, 5)}$.
   - $\text{Finish}[P_0] = \text{true}$.
6. **Test $P_2$**: $\text{Need}[P_2] = (6, 0, 0) \le (7, 5, 5) \implies \mathbf{TRUE}$.
   - $P_2$ executes and finishes.
   - $\text{Work} = (7, 5, 5) + (3, 0, 2) = \mathbf{(10, 5, 7)}$ (Matches Total Resource Vector!).
   - $\text{Finish}[P_2] = \text{true}$.

**Conclusion**: All processes finished ($\text{Finish}[i] = \text{true} \ \forall i$). The system is in a **SAFE STATE** with Safe Sequence:
$$\mathbf{\langle P_1, P_3, P_4, P_0, P_2 \rangle}$$

---

### Step 3: Handle a Dynamic Resource Request
*Suppose process $P_1$ requests: $\text{Request}[P_1] = (1, 0, 2)$. Can this request be granted immediately?*

1. **Condition 1 Check**: $\text{Request}[P_1] \le \text{Need}[P_1] \implies (1, 0, 2) \le (1, 2, 2) \implies \mathbf{TRUE}$.
2. **Condition 2 Check**: $\text{Request}[P_1] \le \text{Available} \implies (1, 0, 2) \le (3, 3, 2) \implies \mathbf{TRUE}$.
3. **Speculative Modification**:
$$\text{Available}' = (3, 3, 2) - (1, 0, 2) = \mathbf{(2, 3, 0)}$$
$$\text{Allocation}'[P_1] = (2, 0, 0) + (1, 0, 2) = \mathbf{(3, 0, 2)}$$
$$\text{Need}'[P_1] = (1, 2, 2) - (1, 0, 2) = \mathbf{(0, 2, 0)}$$

4. **Run Safety Algorithm on New State**:
   - $\text{Work} = (2, 3, 0)$.
   - Check $P_0$: $\text{Need}(7, 4, 3) \le (2, 3, 0) \implies \text{No}$.
   - Check $P_1$: $\text{Need}'(0, 2, 0) \le (2, 3, 0) \implies \mathbf{YES}$.
     - $\text{Work} = (2, 3, 0) + (3, 0, 2) = (5, 3, 2)$. $\text{Finish}[P_1] = \text{true}$.
   - Check $P_3$: $\text{Need}(0, 1, 1) \le (5, 3, 2) \implies \mathbf{YES}$.
     - $\text{Work} = (5, 3, 2) + (2, 1, 1) = (7, 4, 3)$. $\text{Finish}[P_3] = \text{true}$.
   - Check $P_4$: $\text{Need}(4, 3, 1) \le (7, 4, 3) \implies \mathbf{YES}$.
     - $\text{Work} = (7, 4, 3) + (0, 0, 2) = (7, 4, 5)$. $\text{Finish}[P_4] = \text{true}$.
   - Check $P_0$: $\text{Need}(7, 4, 3) \le (7, 4, 5) \implies \mathbf{YES}$.
     - $\text{Work} = (7, 4, 5) + (0, 1, 0) = (7, 5, 5)$. $\text{Finish}[P_0] = \text{true}$.
   - Check $P_2$: $\text{Need}(6, 0, 0) \le (7, 5, 5) \implies \mathbf{YES}$.
     - $\text{Work} = (7, 5, 5) + (3, 0, 2) = (10, 5, 7)$. $\text{Finish}[P_2] = \text{true}$.

**Verdict**: The speculative state is safe with sequence $\langle P_1, P_3, P_4, P_0, P_2 \rangle$. **The request can be granted immediately**.

## 6. Deadlock Detection and Recovery

If an OS does not use prevention or avoidance, it must periodically run a **Deadlock Detection** algorithm and initiate **Recovery**.

### Wait-For Graph (For Single-Instance Systems)
Derived from the Resource Allocation Graph by removing resource nodes and collapsing edges:
$$\text{Edge } P_i \to P_j \text{ exists in Wait-For Graph} \iff P_i \text{ is waiting for a resource held by } P_j$$

$$\text{Cycle in Wait-For Graph} \iff \text{Deadlock exists } (O(n^2) \text{ cycle detection via DFS})$$

```
    Resource Allocation Graph                       Wait-For Graph
         [ R1 ]                                        ( P1 )
        ↗      \                                      ↗      \
       /        ▼                                    /        ▼
    ( P1 )     ( P2 )                             ( P3 )     ( P2 )
       ▲        /                                    ▲        /
        \      ↙                                      \      ↙
         [ R2 ]                                        ( P4 )
```

### Recovery Strategies
When a deadlock is detected, the OS recovers via:
1. **Process Termination**:
   - **Abort all deadlocked processes**: Guaranteed to break deadlock, but causes high computational loss.
   - **Abort one process at a time**: Abort a process and re-run detection until the cycle is resolved. Criteria for selecting victim: Process priority, execution time consumed, resources held, resources needed to finish.
2. **Resource Preemption**:
   - **Selecting a Victim**: Determine which process holding resources will impose minimal cost penalty if preempted.
   - **Rollback**: Roll back the victim process to a safe checkpoint state. Requires checkpointing overhead.
   - **Starvation Avoidance**: Ensure a single process is not repeatedly chosen as the victim by including a retry counter in the victim selection cost function.

## 7. High-Yield Exam Formulas & Invariants

### 1. Minimum Resources to Prevent Deadlock
Given $n$ processes, each requiring at most $k$ units of a single resource type $R$:
$$\text{Maximum resources held without any process finishing} = n \cdot (k - 1)$$
To guarantee that at least one process acquires $k$ units and completes:
$$R_{\text{min}} \ge n \cdot (k - 1) + 1$$

*Example*: If 3 processes each need 4 units of a tape drive, what is the minimum number of tape drives required to guarantee freedom from deadlock?
$$R_{\text{min}} = 3 \cdot (4 - 1) + 1 = 3 \cdot 3 + 1 = \mathbf{10 \text{ tape drives}}$$

### 2. Variable Maximum Demands Formula
If process $P_i$ requires maximum $m_i$ resources:
$$\text{Deadlock-Free Invariant}: \sum_{i=1}^n (m_i - 1) < \text{Total Resources } R$$
Or equivalently:
$$R \ge \sum_{i=1}^n (m_i - 1) + 1$$

## 8. UGC NET & Bihar STET PYQ Analysis & Practice

### Question 1 (UGC NET Official PYQ)
A system has 4 processes and 6 allocatable resource units of the same type. The maximum requirement of each process is 2 units. Can the system ever face a deadlock?
- **A)** Yes, always
- **B)** Yes, under specific scheduling orders
- **C)** No, deadlock is impossible
- **D)** Insufficient data

**Answer**: **C**
**Explanation**:
Using the formula $R_{\text{min}} = n \cdot (k - 1) + 1$:
$$R_{\text{min}} = 4 \cdot (2 - 1) + 1 = 4(1) + 1 = 5 \text{ units}$$
Since the system provides $6$ units and $6 \ge 5$, at least one process will always acquire its maximum 2 units, finish, release its resources, and allow all remaining processes to complete. Deadlock is mathematically impossible.

### Question 2 (Bihar STET Higher Secondary Exam)
Which of the following conditions is negated by requiring processes to acquire all needed resources before execution begins?
- **A)** Mutual Exclusion
- **B)** Hold and Wait
- **C)** Circular Wait
- **D)** No Preemption

**Answer**: **B**
**Explanation**: Requiring a process to request all its resources at once prevents it from holding a subset while waiting for others, directly eliminating the **Hold and Wait** condition.

### Question 3 (UGC NET Algorithm Analysis)
What is the time complexity of the Safety Algorithm in the Banker's Algorithm for $n$ processes and $m$ resource types?
- **A)** $O(m \cdot n)$
- **B)** $O(m \cdot n^2)$
- **C)** $O(m^2 \cdot n)$
- **D)** $O(n^3)$

**Answer**: **B**
**Explanation**: In the worst case, searching through the $n$ processes takes $n$ steps in each of the $n$ iterations, and each step requires comparing $m$ resource dimensions: $O(m \cdot n^2)$.
